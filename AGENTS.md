## General

Follow good design principles (DESIGN_PRINCIPLES.md if present), especially
when reviewing code. The reviewer is the last line of defense and must be
particularly attentive to the rules of the trade and good practices.

When proposing alternatives, always mention associated trade-offs and caveats.

## Communications with humans

When communicating to a human in documentation, code comments or prompt
replies, be brief and clear:
- Avoid exposing too much details or digressing. Be to the point
- Avoid a compressed declarative language. Talk more naturally like a human
  would. Choose the phrasing that a thoughtful, articulate person would
  naturally use.

## Long-haul tasks

If a tasks will require significant work and potentially multiple sessions,
there is a need to plan in advance what will be done and document what has
been done. This help both the user for validating the direction of the work
and you for keeping a memory of what has been done and what remains.

Do not clutter the plan with technical details or design descriptions. Keep
those into specific documents.

Once the plan is approved, it can only be change with the express approval of
the user.

Work can be transfered to a different machine or a different model. Keeping
important knowledge or information in memory only is discouraged.
Documentation inside the project should be sufficient to pick up the work
while having a good grasps of previous work, rules related to the projects and
lessons learned.
